## 용어 정리

- 종단간 테스트(End-to-End test, E2E): 사용자의 요청부터 데이터 저장과 외부 연동 결과까지 전체 흐름을 확인하는 테스트다.
- 멱등성(idempotency): 같은 요청이나 이벤트가 여러 번 들어와도 최종 결과가 한 번 처리한 것과 같게 유지되는 성질이다.
- 계약 테스트(contract test): 두 시스템이 주고받는 주소, 요청, 응답, 오류 형식이 실제로 서로 맞는지 확인하는 테스트다.
- 아웃박스(outbox): 업무 데이터와 발행할 이벤트를 같은 데이터베이스 작업으로 저장한 뒤, 별도 전달 과정이 안전하게 Kafka로 보내는 방식이다.
- P0/P1/P2: P0는 금액·재고·보안처럼 즉시 막아야 할 문제, P1은 정확성·복원력 문제, P2는 계약 품질·유지보수 문제를 뜻한다.

## 1. 조사 방법과 판정 기준

### 조사 방법

1. `docs/design/01-requirements.md`와 실제 Controller를 대조했다.
2. 도메인·애플리케이션·인프라 코드를 정적으로 추적했다.
3. 테스트 클래스가 어떤 성공·실패 경로를 실제로 검증하는지 확인했다.
4. 전체 Gradle 테스트를 강제 재실행했다.
5. HTTP, 데이터베이스, Redis, Kafka, PG 사이의 상태 전이를 따라가며 불변식을 확인했다.

### 상태 표기

| 상태 | 의미 |
|---|---|
| 검증됨 | 현재 테스트가 대표 성공 경로와 핵심 결과를 직접 확인한다. 해당 기능에 결함이 전혀 없다는 뜻은 아니다. |
| 부분 검증 | 일부 성공 경로만 있거나, mock 때문에 실제 인프라 경로를 통과하지 않는다. |
| 미검증 | 구현은 있으나 해당 진입점 또는 주요 실패 경로 테스트가 없다. |
| 결함 확인 | 코드상 잘못된 상태 전이·계산·검증 누락이 확인됐다. 먼저 실패 테스트로 재현해야 한다. |
| 미구현 | 요구사항에는 있으나 외부에서 사용할 진입점 또는 핵심 로직이 없다. |

### 5.2 P1 — 정확성·동시성·복원력

| 번호 | 확인된 사실 또는 강한 위험 | 필요한 수정과 검증 |
|---|---|---|
| P1-1 | `Coupon.useCoupon`은 잔여 수량을 검사하지 않는다. 할인 계산기도 주문 최종액에 연결되지 않았다. | 수량 1에 동시 요청, 0 이하 방지, 주문 할인액·최종액 테스트 |
| P1-2 | 좋아요 count 쿼리에 `deletedAt is null` 조건이 없어 취소한 soft-delete 행도 현재 집계에 포함된다. 관계·`likeCount`·outbox도 한 유스케이스로 묶이지 않았다. | 유효 좋아요만 집계, DB unique, 한 트랜잭션과 API 테스트 |
| P1-3 | 정규화 결과는 관계 count를 표시하지만 좋아요순 정렬은 `product.likeCount`를 사용한다. | 같은 데이터 원천으로 표시·정렬하고 불일치 fixture로 검증 |
| P1-4 | 상품 목록 Redis 키가 `size`를 빼고 브랜드 배열 순서를 그대로 쓴다. 좋아요 변경 시 상세/목록 캐시도 무효화하지 않는다. | `size=10/100`, 브랜드 순서 변경, 좋아요 전후 cache hit 테스트 |
| P1-5 | Redis 랭킹 ID를 DB `IN` 조회한 뒤 순서를 복원하지 않는다. 없는 상품·빈 Redis 결과에 대한 명시적 정책과 테스트도 없다. | Redis 점수 순서, 일부 상품 삭제, 빈 키, 페이지 경계 테스트 |
| P1-6 | 일간 랭킹은 기존 점수를 누적하지 않고 새 배치 점수로 덮어쓴다. 다음 날 이관도 내일 키를 읽고 다시 내일 키에 쓴다. | 여러 배치 누적과 오늘→내일 seed 테스트 |
| P1-7 | 주·월 배치 processor가 일간 행마다 누적 중간 결과를 만들고 입력 순서로 rank를 준다. 기존 테스트는 상품당 일간 행 1개라 결함을 가린다. | 한 상품에 여러 날짜를 넣어 최종 1행·합산 점수·정확한 순위 검증 |
| P1-8 | 지표 멱등 처리가 Redis List와 TTL 3초에 의존하며 원자적·영속적이지 않다. 랭킹은 멱등 처리가 없다. | 동일 eventId 동시/지연 재전달, 재시작, TTL 이후 재전달 테스트 |
| P1-9 | Kafka consumer에 명시적인 오류 처리기, backoff, DLT가 없고 테스트에서는 listener를 끈다. | 역직렬화 오류, poison event, batch 중 1건 실패, retry/DLT/ACK 검증 |
| P1-10 | 양수지만 재고가 없는 상품은 map 조회 후 NPE가 날 수 있다. | 존재하지 않는 양수 productId를 업무 오류로 반환하는 테스트 |
| P1-11 | 포인트 충전은 잠금/버전 없이 읽고 더하며, 회원 ID와 주문번호의 DB unique 보장도 찾지 못했다. | 동시 충전, 동시 가입, 주문번호 충돌 테스트와 DB 제약 |
| P1-12 | 공개 조회 요구사항과 인증 설정이 충돌하고, 헤더 없음·빈 값·잘못된 형식의 오류 코드가 서로 다르다. | 공개/보호 경로 표, 401·403·404 계약 테스트 |
| P1-13 | 주문·결제 DTO에 Bean Validation과 `@Valid`가 부족하며 다수의 `IllegalArgumentException`이 500이 될 수 있다. | null·빈 목록·0·음수·잘못된 enum/날짜/ID의 일관된 400 테스트 |
| P1-14 | Feign URL과 callback URL이 localhost로 고정되고 실제 직렬화·timeout·오류 디코딩 테스트가 없다. | 환경 설정 이동, WireMock/MockWebServer 계약 테스트 |
| P1-15 | PG simulator의 실패·지연·결과가 무작위라 실패 테스트를 재현하기 어렵다. | test profile에서 결과·지연·오류를 명시적으로 선택하도록 변경 |
| P1-16 | 브랜드 상세가 상품 전체를 페이지 제한 없이 읽고 상품마다 좋아요 count를 조회한다. | 최대 20개 정책과 query count/N+1 테스트 |

### 5.3 P2 — API 계약과 유지보수

- 회원 가입과 내 정보 응답의 이메일 필드 이름을 통일한다.
- 포인트 충전은 이미 정의된 요청 DTO를 사용하고 숫자 본문만 받는 계약을 제거한다.
- 결제 응답도 공통 `ApiResponse`와 명시적인 상태 코드를 사용한다.
- `/denormalization`, `/redis`처럼 구현 방법이 노출된 비교용 URL은 내부/성능 실험 프로필로 분리한다.
- 상품·브랜드 응답에서 도메인 record 직접 노출을 중단하고 API 전용 DTO를 둔다.
- 오류 응답에 안정적인 업무 오류 코드를 두고 카드번호·비밀번호·내부 예외 메시지가 노출되지 않게 한다.
- 사용되지 않는 결제 방식 `CASH`, 재고 상태 `STOP_SALE`, 실제 발행 경로가 없는 `PRODUCT_VIEW`·`PRODUCT_SALE_CANCEL` 이벤트와 user event는 구현할지 제거할지 결정한다.

### 7.2 대용량·운영 관점에서 추가 권장 기능

다음은 현재 요구사항의 직접 누락이라기보다 운영 안전성을 위한 권고다.

- 결제 상태/시도 이력 조회와 PG-로컬 상태 재조정(reconciliation) 작업
- 주문 취소·결제 취소·환불 상태 머신과 멱등 보상
- Kafka outbox relay, 지수 backoff 재시도, 실패 격리용 사망 메시지 토픽(Dead Letter Topic, DLT)
- PG callback 서명 검증과 재전송 상태 저장
- Redis 장애 시 DB fallback 및 캐시 오류 격리 정책
- trace ID, 주문번호, 결제 거래키, eventId를 연결한 구조화 로그
- 주문·결제·outbox·Kafka consumer lag·Redis hit ratio 메트릭과 경보
- 관리자용 상품·재고·쿠폰 변경 API의 필요 여부와 권한 모델 확정

## 8. 실행 계획

### Phase 0 — 기준선과 요구사항 고정

목표: 무엇을 구현·검증하는지 한 장의 매트릭스로 고정한다.

작업:

1. 이 문서의 기능 표를 `구현됨/부분 구현/미구현`과 `검증됨/부분 검증/미검증`으로 CI 기준선에 반영한다.
2. `/v3/api-docs`를 저장하고 현재 HTTP 계약을 snapshot으로 남긴다.
3. 인증을 학습용 헤더로 유지할지 실제 인증을 구현할지 결정한다.
4. 카테고리·검색·광고·관리자 API를 이번 범위에 포함할지 결정한다.
5. JaCoCo를 도입하되 전체 숫자만 보지 않고 P0 클래스의 분기 누락을 먼저 확인한다.

완료 기준:

- 모든 요구사항에 담당 API, 구현 상태, 테스트 상태가 연결된다.
- P0 테스트 목록이 이슈 또는 작업 카드로 등록된다.
- 전체 테스트와 OpenAPI 계약을 CI에서 재현할 수 있다.

### Phase 1 — 주문·결제 불변식 복구

목표: 즉시 실행을 막는 P0와 금액·소유권·포인트·쿠폰·재고·결제 불변식을 먼저 복구한다.

작업 순서:

1. 주문항목에 주문 시점 단가를 저장하고 주문 총액·할인액·최종 결제액을 서버가 계산한다.
2. 결제 시 주문 소유 회원과 서버 계산 금액을 검증한다.
3. POINT 결제의 카드 검증을 분리하고 모든 금액의 null·0·음수 정책을 정의한다.
4. 포인트 차감과 주문·결제 성공 상태 전이를 하나의 원자적인 업무 처리로 만든다.
5. 쿠폰 검증·사용을 주문 커밋 전에 수행하고 실패 시 주문·재고를 모두 롤백한다.
6. 결제 idempotency key, PG transaction key unique 연결, callback의 유효 상태 전이를 구현한다.
7. 실패 보상을 멱등하게 만들고 재고 상태·중복 품목·쿠폰 복구량을 바로잡는다.
8. Kafka consumer 통합 테스트보다 먼저 `ProductMetrics` 카운터 초기값과 판매 취소 계산을 수정하고 회귀 테스트를 추가한다.
9. local 외 환경에서 `ddl-auto: create`를 금지하고, 운영 profile 누락 시 안전하게 기동을 거부하도록 설정 검증을 추가한다.
10. 비밀번호를 단방향 해시로 저장하고 회원 ID의 DB unique 제약과 동시 가입 테스트를 추가한다.
11. 운영 범위라면 `X-USER-ID` 신뢰를 실제 인증 주체로 대체하고, 카드번호 저장 금지/토큰화·응답 마스킹을 적용한다.
12. PG callback URL을 URI로 파싱해 정확한 scheme/host/port 허용 목록만 호출하게 한다.

필수 테스트:

- 타 회원 주문, 금액 변조, 잔액 부족, 쿠폰 소진, 재고 부족
- 정상 POINT 결제 후 실제 DB 포인트가 정확히 한 번 차감됨
- 동일 주문 동시 결제, 동일 멱등키 재요청
- 성공/실패 callback 중복 및 역순
- 보상 전후 `초기 재고 = 현재 재고 + 확정 판매 수량`
- 보상 전후 쿠폰 수량과 회원 쿠폰 상태 불변식

완료 기준:

- 이 Phase 범위의 P0 테스트가 수정 전 실패하고 수정 후 통과한다. outbox P0는 Phase 3에서 닫는다.
- 어떤 결제 실패도 거짓 2xx나 추적 불가능한 영구 `PENDING`을 만들지 않는다.
- 동일 요청·이벤트 반복이 금액·재고·쿠폰을 한 번만 변경한다.

### Phase 2 — Web API 계약과 빠진 사용자 기능

목표: 사용자가 호출할 수 있는 기능과 요구사항을 일치시킨다.

작업:

1. 상품·브랜드 공개 GET과 회원 전용 API를 명시적으로 분리한다.
2. 인증 실패 401, 권한 부족 403, 미존재 404, 잘못된 입력 400 정책을 통일한다.
3. 주문·결제·포인트 요청에 API 전용 DTO와 Bean Validation을 적용한다.
4. 좋아요 등록·취소·내 목록 API를 원자적인 유스케이스에 연결한다.
5. 회원별 주문 목록·상세 API를 소유권 검증과 함께 연결한다.
6. 브랜드/상품 목록의 최대 페이지 크기 20과 검색·카테고리 범위를 반영한다.
7. 비교용 구현 URL은 내부 성능 실험 경로로 이동한다.

완료 기준:

- 요구사항의 사용자 기능마다 성공·인증·권한·입력·미존재 Web 테스트가 있다.
- OpenAPI와 실제 응답이 일치한다.
- 잘못된 입력이 500 또는 내부 예외 문자열로 노출되지 않는다.

### Phase 3 — Kafka 아웃박스와 Redis 신뢰성

목표: 이벤트와 캐시가 장애·중복·재시작 상황에서도 결과를 잃거나 왜곡하지 않게 한다.

작업:

1. outbox payload를 최초 업무 데이터와 같은 트랜잭션에서 완성해 저장한다.
2. Kafka broker ACK 성공 후에만 outbox를 `COMPLETED`로 변경한다.
3. PENDING/FAILED를 읽는 relay, lease, retry, backoff, 최대 시도와 DLT를 구현한다.
4. consumer의 역직렬화 오류, batch 일부 실패, 수동 ACK 정책을 명시한다.
5. eventId 기반의 영속적·원자적 멱등 저장을 구현한다.
6. Redis 상품 목록 키에 `size`와 정규화한 필터를 포함하고 쓰기 후 캐시 무효화를 연결한다.
7. Redis 오류 시 DB fallback 여부와 허용할 stale 시간 정책을 정의한다.

필수 테스트:

- producer ACK 성공/실패와 outbox 상태
- relay 중간 종료 후 재시작, 같은 event 두 consumer의 동시 처리
- poison event와 DLT, batch 중 한 건 실패
- 캐시 miss→fill→hit, size/필터 키 분리, like 변경 무효화
- Redis 중단 중 조회와 복구 후 재사용

완료 기준:

- 브로커 장애 중 이벤트가 `COMPLETED`로 잘못 기록되지 않는다.
- 재시작과 중복 배달 후에도 최종 업무 상태가 한 번 처리한 것과 같다.
- 캐시 사용 여부와 무관하게 사용자 응답 의미가 같다.

### Phase 4 — 스트리머 지표와 랭킹 정확성

목표: 좋아요·조회·판매 지표와 일/주/월 랭킹이 입력 순서나 batch 크기에 관계없이 같다.

작업:

1. `ProductMetrics` 카운터를 0으로 초기화하고 판매 취소 계산을 수정한다.
2. 이벤트 하나가 어떤 지표를 얼마나 바꾸는지 도메인 표를 만든다.
3. 일간 Redis 점수를 원자적으로 누적하고 오늘 점수를 내일로 이관한다.
4. 주·월 batch는 `(productId, period)`별 최종 1행으로 집계한 뒤 전체 점수로 rank를 계산한다.
5. Redis 순위 ID 순서를 DB 결과에서 명시적으로 복원한다.
6. 오래된 이벤트, 중복 이벤트, 누락 상품, 동점 순위 정책을 정한다.

완료 기준:

- 동일 데이터는 batch 크기·분할·입력 순서에 관계없이 같은 점수와 순위를 만든다.
- 각 기간에 상품당 결과가 정확히 1행이다.
- Redis와 API 응답 순서가 같다.

### Phase 5 — Feign/PG 실제 계약과 전체 E2E

목표: mock 밖의 실제 HTTP 실패와 전체 시스템 최종 상태를 검증한다.

작업:

1. PG base URL, callback URL, timeout을 환경 설정으로 이동한다.
2. WireMock 또는 MockWebServer로 요청 JSON, 응답 JSON, 4xx/5xx, timeout, 잘못된 payload를 검증한다.
3. PG simulator의 결과·오류·지연을 test profile에서 결정적으로 선택하게 한다.
4. callback 전달에도 outbox/재시도/최종 실패 상태를 둔다.
5. commerce API, PG, MySQL, Redis, Kafka를 함께 띄워 전체 흐름을 테스트한다.

전체 E2E 시나리오:

`가입 → 포인트/쿠폰 준비 → 주문 → 결제 요청 → PG 처리 → callback → 주문·결제·재고·쿠폰·outbox 최종 확인`

장애 시나리오:

- PG timeout 뒤 재시도
- callback 일시 실패 뒤 재전송
- Kafka 중단 중 주문 후 복구
- Redis 중단 중 상품 조회
- 애플리케이션 재시작 전후 PENDING 복구

완료 기준:

- mock 없이 대표 성공·실패 흐름이 CI에서 재현 가능하다.
- HTTP 응답뿐 아니라 모든 저장소의 최종 불변식을 확인한다.

### Phase 6 — 성능·관측성 실험

목표: 이미 마련된 `docs/performance`의 k6·Prometheus·Grafana 실험실을 확장하고, 정확성 수정 전후의 병목과 한계를 같은 조건에서 다시 측정한다.

측정 항목:

- 처리량(초당 요청 수), 오류율, p50/p95/p99 응답시간
- 데이터베이스 connection pool 대기, query 수, slow query, lock 대기와 deadlock
- Redis hit ratio, 명령 지연, memory, eviction
- Kafka producer 실패, consumer lag, 처리율, retry/DLT 수
- JVM heap, garbage collection 정지 시간, CPU, thread pool·HTTP connection pool 포화도
- 결제 최종 완료 시간과 callback 지연 분포

실험 순서:

1. 상품 목록 정규화·비정규화·Redis 경로를 같은 데이터와 부하로 비교한다.
2. 상품 상세 cache cold/warm, 좋아요 동시 쓰기, 주문 동시 생성, 결제 callback burst를 분리 측정한다.
3. 정상 부하, 단계 증가 부하, 순간 폭증, 장시간 안정성, Redis/Kafka/PG 지연 주입을 실행한다.
4. Prometheus와 Grafana에 요청·DB·Redis·Kafka·JVM·업무 불변식 패널을 연결한다.

완료 기준:

- 각 API의 목표 처리량·p95·p99·오류율 기준이 문서화된다.
- 한계를 넘었을 때 어느 자원이 먼저 포화되는지 재현 가능하다.
- 성능 개선 전후를 같은 스크립트와 대시보드로 비교할 수 있다.

## 9. 계층별 추가 테스트 목록

### 도메인 단위 테스트

- `Point`: 0·음수 사용/충전, 잔액 경계
- `Payments`: CARD/POINT별 필수값, 0·음수 금액, 허용/금지 상태 전이
- `Coupon`: 수량 1→0, 0에서 사용 거부, 중복 rollback
- `Inventory`: 1→0 `SOLD_OUT`, rollback 후 `IN_SALE`, 중복 rollback
- `ProductMetrics`: 첫 이벤트, 취소, 음수 방지
- 주문 금액: 단가 스냅샷, 할인, 반올림 정책

### 애플리케이션 통합 테스트

- 주문 소유권과 서버 결제 금액 검증
- POINT 잔액 부족 시 전체 rollback
- 쿠폰 실패 시 주문·재고 전체 rollback
- 중복 상품 집계와 lock 순서
- 좋아요 관계·count·outbox 한 트랜잭션
- 동일 callback 2회와 성공/실패 역순
- outbox ACK 성공·실패와 relay 재처리

### Web API 테스트

- 상품·브랜드 공개 조회 시 헤더 없음
- 보호 API의 없음/잘못됨/타 회원 헤더
- 모든 DTO의 null·빈 값·0·음수·잘못된 enum
- 좋아요, 주문 목록·상세, 랭킹의 성공/404/권한/페이지 경계
- 공통 오류 응답과 민감정보 비노출
- OpenAPI snapshot 호환성

### Kafka 테스트

- producer serializer와 broker ACK
- consumer deserializer, manual ACK, retry/backoff, DLT
- 같은 eventId의 순차·동시·TTL 이후 재전달
- batch 중 한 메시지만 실패하는 경우
- relay 프로세스 재시작과 lease 만료

### Redis 테스트

- 문자열·목록·정렬 집합 직렬화와 TTL
- 상품 목록 `page/size/filter/sort`별 키 충돌 방지
- 좋아요 변경 후 상세·목록 무효화
- 동점과 0-based/1-based rank 정책
- Redis 순서와 API 순서 일치
- Redis 장애 시 fallback과 복구

### Feign/PG 계약 테스트

- 실제 요청/응답 JSON과 금액 타입
- PG 400/404/409/500, timeout, 잘못된 body
- 회로 차단기의 closed/open/half-open 상태
- POST 재시도 시 idempotency key
- callback 서명·중복·재시도·최종 실패

- 새 테스트가 외부 무작위성이나 실행 순서에 의존하지 않는다.

## 11. 최종 완료 기준

다음 조건을 모두 만족하면 이 감사 계획이 완료된 것으로 본다.

1. P0 결함이 0개이고 각 결함에 회귀 테스트가 있다.
2. 주문·결제·재고·쿠폰·포인트 불변식이 중복·동시성·실패 상황에서도 유지된다.
3. 요구사항의 모든 사용자 기능이 구현 상태와 테스트 상태로 추적된다.
4. Kafka/Redis/Feign의 실제 인프라 통합 테스트가 CI에서 실행된다.
5. 소비자 중복 처리, broker 장애, callback 실패, 애플리케이션 재시작을 재현할 수 있다.
6. 전체 E2E가 mock 없이 대표 성공·실패 흐름을 통과한다.
7. p95/p99, 처리량, 오류율, DB/Redis/Kafka/JVM 지표를 같은 실험으로 반복 비교할 수 있다.

권고 품질 게이트:

- 전체 line coverage는 80% 이상을 출발점으로 삼되 숫자만 목표로 삼지 않는다.
- 결제·주문·쿠폰·재고·포인트·outbox의 핵심 분기 coverage는 90% 이상을 목표로 한다.
- P0 상태 전이에는 변이 테스트를 선택적으로 적용해, assertion이 실제 결함을 잡는지 확인한다.
- flaky test 재실행으로 통과시키는 방식은 허용하지 않고 원인을 기록·수정한다.
